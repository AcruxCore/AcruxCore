# MCP Endpoint

`POST /api/v1/mcp` speaks the [Model Context Protocol](https://modelcontextprotocol.io)
over its Streamable HTTP transport. An MCP client that supports remote servers can point
at it directly and get the whole platform as tools — prompts, the tool catalog, the
gateway, traces and evaluations — without installing anything.

All examples below were verified with real curl output against a running server.

:::note[Authentication is the same bearer key as everywhere else]
Send `Authorization: Bearer acx_sk_…`. Create the key in the dashboard under
**Settings → API keys**. A session cookie is deliberately **not** accepted here — see
[Authentication](/api-reference/authentication).
:::

## Transport rules

- **`POST` only.** `GET` and `DELETE` return `405`. The endpoint is stateless: every
  request builds its own server, so there is no session to delete and no
  server-initiated stream to open.
- Send `Accept: application/json, text/event-stream` — the transport requires it.
- Send `MCP-Protocol-Version: <version>` on every request after `initialize`.
- Responses come back as plain JSON, not SSE frames.

Because it is stateless there is no `Mcp-Session-Id`: any instance behind the load
balancer can answer any request, and a deploy never breaks a client's connection.

### initialize

```bash
curl -X POST $ACRUXCORE_BASE_URL/mcp \
  -H "Authorization: Bearer $ACRUXCORE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"1.0"}}}'
```

Response (status 200) — `instructions` explains the prompt/version/alias model to the
client's model, so it does not have to infer it from the tool names:

```json
{
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "tools": { "listChanged": true },
      "prompts": { "listChanged": false },
      "resources": { "listChanged": true }
    },
    "serverInfo": { "name": "acruxcore", "title": "AcruxCore", "version": "0.1.0" },
    "instructions": "AcruxCore is an LLM-ops platform: a prompt registry, a versioned tool catalog, an AI gateway, tracing, and evaluation.\n\nThree ideas explain almost every tool here:\n- A **prompt** is a named container. It holds no messages itself.\n- A **version** is an immutable commit of that prompt's messages. Version numbers are sequential.\n- An **alias** (\"production\", \"staging\", anything else) is a moving pointer at one version.\n\nCommitting a version never moves an alias — promote_prompt_alias is what ships a change, and promoting an earlier version is how a rollback happens.\n\nRegistry prompts are also exposed through MCP's prompts primitive, so they can be used directly as templates.   "jsonrpc": "2.0",

```

### tools/call — running an experiment

`run_experiment` creates an experiment over a dataset and starts its run. The run tests
every pair of a prompt version in `version_ids` and a model in `models`. `judge_model` is
required, and it must be a model registered in the gateway. `judge_prompt` is optional. It
takes the name or UUID of one of your prompts, and that prompt grades every answer
instead of the built-in judge. The call returns as soon as the run is queued.

```bash
curl -X POST $ACRUXCORE_BASE_URL/mcp \
  -H "Authorization: Bearer $ACRUXCORE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2025-06-18" \
  -d '{"jsonrpc":"2.0","id":8,"method":"tools/call","params":{"name":"run_experiment","arguments":{"dataset_id":"3f04989b-adff-40eb-b86a-d9b5ffc64153","version_ids":["d6f7cca3-b855-4445-8983-269cf7859fdf"],"models":["gpt-4o-mini-or"],"judge_model":"gpt-4o-mini-or","judge_prompt":"ticket-classifier judge","name":"classifier, rubric judge"}}}'
```

### tools/call — improving a prompt with the optimizer

Three tools drive the optimizer. `optimize_prompt` starts a run. In the run, an
optimizer model writes rewrites of the prompt version that `alias` points at (default
`production`). That version is the **baseline**. The judge model then scores each rewrite
and the baseline on the dataset's examples. `prompt` takes the prompt's name or its UUID.
`judge_model` is required. `draft_count` is the number of rewrites to write, 1 to 6
(default 3). `judge_prompt` is optional and works as in `run_experiment`. The optimizer
also reads that judge prompt, so its rewrites aim at the same rubric. The call returns the
run id as soon as the run is queued.

```bash
curl -X POST $ACRUXCORE_BASE_URL/mcp \
  -H "Authorization: Bearer $ACRUXCORE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2025-06-18" \
  -d '{"jsonrpc":"2.0","id":6,"method":"tools/call","params":{"name":"optimize_prompt","arguments":{"prompt":"mcp-optimizer-demo","dataset_id":"9e756ad4-f39b-4b64-98da-03a4cca02354","models":["gpt-4o-mini-or"],"judge_model":"gpt-4o-mini-or","draft_count":2}}}'
```

`promote_optimize_candidate` saves one rewrite as a new prompt version and points `alias`
at that new version. `alias` defaults to the alias the run was scored against. The new
version keeps the baseline version's default model. The tool refuses a rewrite whose
`beatsBaseline` is false. It also refuses when `alias` now points at a different version
than the baseline, because no score compared the rewrite with that version. Setting
`promote_without_improvement: true` overrides both refusals. The tool also refuses while the
run is still queued or running, with no override. Promoting needs the editor role or higher, and the audit
log records the new version and the alias move, as it does for a promote in the
dashboard.

```bash
curl -X POST $ACRUXCORE_BASE_URL/mcp \
  -H "Authorization: Bearer $ACRUXCORE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2025-06-18" \
```

rewrite's `messages` and sets `messagesOmitted: true`. Every `candidateId` and score stays in
the result. Pass `candidate_id` with `run_id` to read one rewrite with its full messages.

JSON object:

### prompts/list — the registry as MCP prompts

Every prompt in the team's registry is also an MCP prompt, resolved at the `production`
alias, with the version's template variables as arguments.

```bash
curl -X POST $ACRUXCORE_BASE_URL/mcp \
  -H "Authorization: Bearer $ACRUXCORE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2025-06-18" \
  -d '{"jsonrpc":"2.0","id":4,"method":"prompts/list","params":{}}'
```

Response (status 200), first two entries:

```json
{
  "result": {
    "prompts": [
      {
        "name": "del-demo-prompt",
        "title": "del-demo-prompt",
        "description": "AcruxCore registry prompt (alias \"production\", version 1)",
        "arguments": [
          { "name": "name", "description": "Template variable \"name\".", "required": true }
        ]
      },
      {
        "name": "support-reply",
        "title": "support-reply",
        "description": "Draft the reply a support agent sends to an inbound customer message. (alias \"production\", version 2)",
        "arguments": [
          { "name": "message", "description": "Template variable \"message\".", "required": true }
        ]
      }
    ]
  },
  "jsonrpc": "2.0",
  "id": 4
}
```

`prompts/get` renders one, and returns the messages. MCP's message role is `user` or
`assistant` only — there is no system role in the protocol — so a template's system
message comes back as the leading `user` message with its text unchanged.

A registry of more than 25 prompts is paged: the result carries `nextCursor`, which goes
back as `params.cursor`.

### Resources

Two resource templates are registered:

| URI template | Content |
|---|---|
| `acruxcore://prompts/{name}/{alias}` | The raw, unrendered template of the version an alias points at, with its variables and bound default model. |
| `acruxcore://traces/{traceId}` | One trace with its full span tree. |

`resources/list` enumerates one entry per registry prompt at the default alias. Traces
are deliberately not enumerated — a team accumulates them without limit — so find one
with `search_traces` and address it by id.

### Error responses

No `Authorization` header (status 401):

```json
{ "error": { "code": "UNAUTHORIZED", "message": "API key required." } }
```

`GET` or `DELETE` (status 405):

```json
{
  "jsonrpc": "2.0",
  "error": { "code": -32000, "message": "Method not allowed. This MCP endpoint is stateless — use POST." },
  "id": null
}
```

A tool that fails comes back as a **successful** JSON-RPC response carrying
`isError: true`, which is how MCP reports tool failures — the calling model sees the
error and can act on it. The AcruxCore error code and message are passed through intact:

```json
{
  "result": {
    "content": [
      {
        "type": "text",
        "text": "AcruxCore API error (VALIDATION_ERROR)\nRequest: POST /gateway/chat/completions\nStatus: 400\nMessage: model is required"
      }
    ],
    "isError": true
  },
  "jsonrpc": "2.0",
  "id": 5
}
```

### Local alternative

Clients that only speak stdio can run the same server locally:

```bash
npx -y @acruxcoreai/mcp-server
```

with `ACRUXCORE_API_KEY` and `ACRUXCORE_BASE_URL` in the environment. The stdio package
adds two options the hosted endpoint has no way to express: `--toolsets` to narrow the
surface, and `--read-only` to drop every mutating tool from the listing. See
[Connect an MCP client](/docs/guides/connect-an-mcp-client).
